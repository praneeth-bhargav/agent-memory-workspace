01 / The big picture

A memory layer, not a second database of everything.

Agent combines durable, free-text memory with live access to structured workspace data. The agent chooses the right tool for the question.

InputConversation or source record
→
AgentLangChain + LangGraph tool orchestration
→
Two pathsSemantic memory or current SQL / search
→
OutputAnswer + verified source links when available
Design intent: Remember useful context that a fresh source query cannot reliably reconstruct. Query the source of truth for current records.

02 / Storage & retrieval

Text is the memory. Vectors help find it.

SQLite holds the record; embeddings are an index for semantic similarity, not a separate fact schema.

01 · StoreFree-text memories in SQLite memories
→
02 · EmbedOpenAI embeddings cached in semantic_vectors
→
03 · Ranksqlite-vec cosine distance ranks active candidates
→
04 · SelectModel chooses relevant results from up to 8 candidates

Cache lifecycle

Text hash and embedding model identify stale vectors. Changed memory text is embedded again when needed.

Actual implementation

Vectors are stored as JSON in SQLite and staged into a temporary candidate table for sqlite-vec scoring. This is not a persistent ANN vector index.

Implementation: memory_layer/semantic.py, memory_layer/store.py

03 / Automatic memory

The user need not say “remember.”

The agent is instructed to notice durable facts and preferences in ordinary conversation and proactively invoke its memory-change tool.

User says“End my emails with Best & Regards.”
→
Agent callsmemory_change with a semantic query
→
DecisionRetrieve candidates; model selects create / update / none / clarify
→
CommitValidate target, source and snapshot; write atomically
Also supported

Explicit requests

“Remember this” and corrections enter the same memory-change path; forget requests have suppression safeguards.

Other input

Source review

After relevant reads, a bounded model review may save useful durable source facts. This is separate from direct user statements.

Not guaranteed: A model chooses when to call the tool and what to retain. It can miss facts or make incorrect changes.

Implementation: memory_layer/agent.py, memory_layer/service.py, memory_layer/source_memory.py

04 / Memory boundaries

What belongs in memory?

This is a design preference implemented through prompts and model decisions—not a hard classifier that prevents every duplicate.

Remember

Durable context

  • User preferences, identity and corrections.
  • Useful decisions, commitments and time-bounded assignments when supported by evidence.
  • Context valuable later and not reliably reconstructed by a fresh query.
Prefer live lookup

Current source records

  • Calendar availability, contacts, structured counts and current event fields → SQL / calendar tools.
  • Email and Slack content → FTS or targeted source tools.
  • Routine transient details or unsupported inferred facts → do not intentionally store.
Important nuance: The model can still store a useful source-derived fact even when its original record remains queryable. This is not a strict SQL-exclusion rule.

Implementation: memory_layer/agent.py, memory_layer/source_memory.py, memory_layer/source_query.py

05 / Orchestration

Start with memory. Give the agent tools.

The memory service was built as a standalone capability, then exposed to a LangChain agent running on LangGraph.

Memory first

Independent service

MemoryLayer provides read and change operations over storage, semantic candidates and model decisions.

Tool interface

Agent-facing tools

memory_read and memory_change are the actual tool names—conceptually get memory and change memory.

Runtime

LangChain + LangGraph

create_agent orchestrates tools; a SQLite checkpointer keeps separate chat state. Long-term memory is shared.

Not a rigid workflow: The model chooses tools from instructions. It can use memory, SQL, FTS and source-specific tools; routing is not guaranteed.

06 / Citations

Trace a claim back to its source.

Provenance is recorded at memory-write time; answer links are selected and checked against records actually retrieved in the current turn.

CaptureSource facts carry message / event IDs; chat facts link to original user messages.
→
Re-fetchmemory_read can include the current source record or a missing-record indication.
→
GroundA model assesses the proposed answer using current-turn evidence.
→
ValidateApplication filters references to IDs present in retrieved records; UI opens the source.
Boundary: A valid citation identifies a record; it does not prove the model interpreted it correctly. Availability slots do not themselves have calendar-event IDs.

07 / Time & limitations

History exists. Time travel does not.

Auditability and time-aware retrieval are different capabilities.

Stored

Change history

memory_history records create, update and delete actions with timestamps. It is an audit log—not the memory retrieval source.

Limited

Dated facts

Distinct effective dates can be retained as separate free-text memories. Search ranks semantically; it has no exact effective-date filter.

Not provided

Point-in-time answers

There is no general “what did we believe on this date?” query or temporal versioned fact model. Retrieval can miss or confuse older facts.

Other limits: Forgetting deactivates and suppresses memory; it is not guaranteed erasure from transcripts, providers or backups. Synthetic data only.

Implementation: memory_layer/store.py, memory_layer/service.py, memory_layer/semantic.py

08 / Explicit tradeoffs

Simple and flexible, with measurable costs.

Free text over structured facts

Gain: Handles open-ended preferences and nuanced context without a predefined schema.
Cost: Harder exact filtering, deduplication, contradiction resolution and temporal reasoning.

Model judgment over fixed rules

Gain: Can recognize implicit durable facts and select context flexibly.
Cost: Misses, false positives and inconsistent grounding. Tool choice is probabilistic.

sqlite-vec over a separate vector service

Gain: A portable local SQLite deployment and fewer infrastructure components.
Cost: Candidate staging and scoring are not a persistent ANN index; scaling is limited.

Source of truth over memory duplication

Gain: Live SQL and source reads can reflect updates.
Cost: More tool calls and model judgments; source-derived memories can still become stale.

These are design consequences of the current implementation, not benchmark results.

09 / Evaluation design

Evaluate behavior and state separately.

Scenario fixtures exercise memory, sources, mock actions, chat isolation, handoffs and stories in disposable databases.

01 · SetupFingerprint synthetic inputs; seed reproducible case state.
→
02 · ExecuteRun real agent turns; collect tool events and before / after state.
→
03 · GradeLLM judge scores behavior and applicable memory outcomes.
→
04 · GateDeterministic checks enforce state and confirmation safety.

Evidence, not just a score

Reports include turn traces, snapshots, check results and pass / fail / blocked / unlabeled / error states. Optional LangSmith experiments upload selected synthetic cases and traces.

Know the limits

LLM judges can be wrong. Some labels are agent-drafted, not independently reviewed. Paid runs are explicit; no full-run improvement is claimed without a new run.

Implementation: evals/run_memory_lab.py, evals/state_checks.py, evals/grading.py, evals/memory_lab/README.md

10 / Takeaway

Remember context.
Query current truth.
Show the evidence.

A compact memory service becomes an agent capability through tools, provenance, and evaluation—not by treating every source record as a memory.

Memory

Free text + semantic candidates + validated changes.

Sources

Live SQL, content search, source tools and traceable citations.

Safety

Mock-only actions, separate confirmation, isolated synthetic evals and explicit limitations.

Prototype boundary: No authentication or multi-user isolation; use synthetic data only. Model and provider calls can carry conversation and memory content.

Source of truth: the repository implementation. This visualizer is a presentation artifact and makes no model calls.

11 / Context compaction

Keep recent context.
Summarize older history.

The agent manages its conversation context separately from durable memories and the visible chat transcript.

01 · TriggerLangChain summarization starts at 24 agent messages, including tool-related messages—not 10 user messages.
→
02 · CompactThe model summarizes older context while the middleware keeps the latest 12 messages.
→
03 · ContinueThe agent uses the summary and retained recent messages for subsequent work.

Separate from memory

Summarization is temporary agent context management; durable free-text memories have their own storage and retrieval path.

Separate from the transcript

Chat messages are stored separately for display. Compaction does not mean every old detail remains available to the model.

Limit: Model-generated summaries can omit or distort details. The threshold counts agent messages, not conversation turns.

Implementation: memory_layer/agent.py, memory_layer/chat_store.py
