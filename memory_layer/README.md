# Standalone memory lab

The local workspace uses its own SQLite database and orchestration. Build the React workspace and start the backend:

```bash
cd frontend && npm install && npm run build && cd ..
uv run uvicorn memory_layer.lab:app --host 127.0.0.1 --port 8013
```

Open `http://127.0.0.1:8013/workspace` for the React chat and source screens. The original minimal chat remains at `/`. The default database is `memory-lab.sqlite3`; set `MEMORY_LAB_DB` before startup to use a separate file. Use one database per user: the lab has no authentication or user isolation.

To replay a bounded chronological sample, use a new disposable database and an explicit provider-enabled development shell:

```bash
~/.local/bin/uv run python -m memory_layer.history_replay --database /tmp/agent-history.sqlite3 --limit 250
```

If interrupted, rerun the same source/model selection with `--resume` and the same database path. Resume requires an exact match for the selected message IDs, timestamps, channels, roles, text, agent model, embedding model, decision prompt, and replay version. Completed messages, source mappings, and outcomes are checkpointed; memory writes and their outcomes commit together. Provider failures leave the current decision pending so it may call the model again on resume. Invalid model decisions are recorded as rejected. Historical replay only calls the memory-decision path; it never invokes chat or mock-action tools. Existing database paths are rejected unless `--resume` is supplied. Do not point replay at the active lab database; back up and obtain separate approval before promoting a staging result.

The workspace reads `/api/sources` from the same database as the agent. It refreshes after tool results and replies, when the page becomes visible, and every five seconds while visible. The workspace supports manual synthetic contact and calendar-event creation and editing, adding incoming email to a new or existing thread, editing its sender, body, timestamp and unread status, changing the shared thread subject, and creating or editing Slack channels and messages. Renaming a channel preserves its messages and memberships, and is blocked while a pending Slack action refers to it. The Persona tab edits one memory directly. For the Playwright check, run an isolated backend/database, then run `WORKSPACE_QA_URL=http://127.0.0.1:PORT npm run test:workspace` in `frontend/`; the check creates synthetic records and uses real model calls. Set `CHROME_PATH` if Chrome is installed elsewhere.

Source records use separate SQLite tables: `contacts`; `slack_people`, `slack_channels`, `slack_members`, and `slack_messages`; `mail_threads`, `mail_messages`, and `mail_recipients`; and `calendar_people` and `calendar_events`. Slack people and contacts are independent. Existing records from the old `mock_source_records` table are copied once into the new tables; the old table is retained but no longer updated. Foreign keys are enforced on application connections.

The LangChain agent exposes memory tools and mock contact, mail, Slack, calendar, availability, and action-preparation tools. Its bounded SQL source tool opens SQLite read-only and authorizes only source tables; the prompt documents source columns and relationships. The agent is instructed to check current records and clarify ambiguous identities, but model compliance is not guaranteed. Reading a source-cited memory includes the current referenced source record (or a missing-record indication) for comparison. After relevant source lookups, a bounded model review considers up to three returned records for useful durable facts; it can also explicitly save a fact from a current mail message, Slack message, or calendar event with a source ID. Explicit requests not to save are respected by these source-memory paths. The source is rechecked atomically before each memory write. This review adds model calls and can miss or misinterpret facts. Source citations identify the record, not proof that the extracted fact is entailed. Before preparing an email, Slack post, or calendar booking, it must retrieve the corresponding `get_action_context` result in the same turn; lookup failure or an unresolved email name/signature placeholder prevents preparation. The agent is instructed to use retrieved preferences, but model interpretation is not guaranteed. Source records are seeded from `data/sources/` into the lab database without overwriting existing records. The supplied `persona.json` time is used as the synthetic scenario's current time. Mock emails, Slack posts, and calendar bookings require a separate explicit confirmation; no external account is contacted. Each chat can have one pending action, and another message in that chat cancels its pending action. Pending actions cannot be confirmed from a different chat.

On first use, profile details from `data/persona.json` seed one `memories` row flagged `is_persona = 1`. The Persona tab calls `GET /api/persona` and `PUT /api/persona` directly; the PUT includes the previously loaded `expected_text` and rejects stale edits. Saving invalidates the cached embedding, which is regenerated on the next semantic search. The seed is not repeated if the persona is later deleted. To avoid accidentally overwriting or deleting the entire profile, chat-driven edits targeting that row ask the user to edit the Persona tab instead. The Memories tab lists active memories and their source links; edits use stale-text checks, invalidate cached embeddings, and remove old provenance rather than claiming it supports the replacement text. Forget is confirmation-gated, keeps the persona protected, marks the memory inactive, and records a suppression entry. The frozen `as_of` is not part of the memory; it and the mock email sender still come from the JSON file at agent startup, so editing persona text does not change them.

The agent is instructed to choose read-only SQL for structured questions, FTS5 for Slack and mail content, and semantic memory for learned facts; this is model-directed, not a guaranteed router or separate classifier. Explicit mail address lookups use a direction-specific `search_mail_by_address` tool (`from`, `to`, or `cc`) that constructs the corresponding parameterized query. When a request explicitly names an address and direction, generic SQL and FTS mail search are blocked in favor of that tool. FTS5 uses Porter stemming and returns at most 50 results, with a truncation flag; all query terms must match and arbitrary typos are not corrected. The agent should broaden unsuccessful content queries. New Slack and incoming-mail timestamps default to the scenario `as_of` unless supplied explicitly.

The agent selects a semantic search query and proactively requests changes for durable facts stated by the user. OpenAI embeddings identify candidates; cosine distance is computed by sqlite-vec inside SQLite. Candidate vectors are staged in a temporary table, while existing JSON embeddings remain cached in `semantic_vectors` and are refreshed when text or model changes. Only active memories are searched; `memory_history` is an audit log, not a retrieval source. Dated assignments are kept separately where their effective dates are identified, but semantic ranking and model interpretation do not provide an exact date filter or guarantee retrieval. Semantic similarity is not proof of a match, and model decisions can be wrong.

Chat-driven memory changes can cite the current user message; confirmed mock-action memory reviews can cite an earlier user message. The model selects a source from the available chat messages, and the application verifies and stores the link atomically with the memory. Answer citations can open the original chat and message. A citation identifies the source, not proof that the model interpreted it correctly; confirmation alone does not establish that a recipient accepted an assignment. A plain “no” cancels a pending mock action without reviewing it for memory.

A LangGraph SQLite checkpointer stores separate conversation context for each chat in the same database. The workspace can create and reopen chats, and separately stores visible messages and tool events so the transcript survives refreshes and restarts. Long-term memories remain shared. The pre-existing `memory-lab` chat is imported as Previous chat; messages already summarized in its latest checkpoint may not be individually recoverable. Existing pending mock actions are moved into that chat. A bounded recent context and LangChain summarization are used for long conversations. The local chat streams real tool starts and results, with expandable input and result details. Tool names, inputs, full results, status, counts, timings, and safe failure types also appear in the server log, grouped by run ID. Memory searches log the query, ranked candidates and similarity scores; memory decisions log the complete model input and parsed result, with run and chat IDs. The model does not explain its decision. Follow the local log with watch the server console and find a run with `rg 'run_id=<id>'` in your captured server log. The UI and logs contain conversation, memory and mock-source content; provider credentials are not intentionally logged.

**Use synthetic data only.** The model alone controls proactive changes, so an error or prompt injection can create, update, or delete the wrong memory. Forgetting marks a memory inactive, preserves its text and audit history, and stores a suppression entry. Before a normal agent turn, checkpoint messages matching a forgotten fact are removed from model context; separate visible chat-event history is retained for explicit browsing. Automatic memory changes, linked-source review, and chronological replay also honor suppression unless the user explicitly asks to remember the fact again. Suppression uses conservative lexical overlap, not semantic identity: paraphrases with too little shared wording may evade it, while unrelated facts sharing most meaningful words may be blocked. This is not guaranteed erasure: raw transcripts, provider records, backups, and filesystem copies remain. This prototype is not safe for unattended use or sensitive data. Messages, memories and embedding inputs are sent to the configured model provider.
